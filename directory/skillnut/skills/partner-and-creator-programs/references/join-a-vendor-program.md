# Module 7 - Join a vendor's program

Load this for Module 7. The other side of the table: the user is an agency, consultant or creator joining a software vendor's partner, expert or creator program, or writing a sponsored post for one. Two paths.

## Path A - Apply to a partner or expert program

1. **Ingest the program.** Read the vendor's program page or email the user pastes. If the brief is behind a login, ask for it; never guess its rules.
2. **Extract levels and gates.** Per level: what it requires (training, active clients, referenceable customers, a trial-workspace assessment, videos), and what it gives (status, directory listing, deal flow, co-selling, a shared channel, marketing support).
3. **Dated checklist.** Every requirement as a row: requirement, evidence needed, owner, due date, status. Put the application deadline at the top. In a real case an application stalled because several steps and videos were left to the end; schedule videos early.
4. **Map proof.** Which current clients are referenceable, and how each may be named (by name, or anonymised by industry and size). Ask the user; never assume permission.
5. **Evidence pack:**
   - A build spec for any trial or demo workspace the vendor will assess (objects, lists, fields, automations, reports), mirroring how the user really works with clients.
   - One short case study per referenceable client (problem, what was built, result in words or the client's approved figures). The **Proof Points by Industry** skill helps with structure.
   - Scripts for walkthrough videos, one per thing the vendor wants shown.
   - Draft answers to the application questions.
6. **Submit and follow up.** The user submits; you keep the checklist and follow-up dates.
7. **After approval.** Directory listing copy, the referral link or code (send it to clients at first touch, so the referral is inside the vendor's attribution window), and how to ask for co-selling.

## Path B - Write a sponsored post from a vendor brief

1. **Parse the brief into a dated table:** ship date, draft due, go-live, the event the call to action points at, rules, approved facts, banned claims, required calls to action and tracked links.
2. **Try the product first.** Half an hour to an hour in the product before writing. Capture one moment that surprised you; that moment is the post.
3. **Pick one angle, don't mix.** Typical angles: the demo (show it working), the industry shift (how the work is changing), the discovery (a surprising result), the workflow comparison (old way vs new way, no competitor names).
4. **Map one to three features** to the user's audience, tied to a real, anonymised client situation.
5. **Draft** with the **LinkedIn Post Generator** skill: story or insight first, the product second, a soft call to action.
6. **Compliance check against the brief:**
   - [ ] The product's web address as plain text, not an @mention (unless the brief says otherwise)
   - [ ] Dedicated to this vendor; no roundup, no competitor names
   - [ ] Approved facts only; nothing from the banned list
   - [ ] Required calls to action and the tracked link present
   - [ ] Soft call to action, not a hard sell
   - [ ] The phase is right (before launch: anticipation; after launch: real experience)
7. **Visuals** if the brief asks: sizes per placement (portrait teaser, square, wide, thumbnail).
8. **Submit the draft at least 48 hours before posting**, through the channel the brief names. Apply the feedback.
9. **Publish** only on the user's go (or the user posts it).
10. **Report back** to the vendor's partner manager: link, date, and the results the platform shows (clicks, engagement), as the user's real numbers.

## Output

Path A: `Vendor program - <program>/` with the checklist, proof map, workspace spec, case studies, video scripts, application answers. Path B: the dated brief table, the chosen angle, the draft, the compliance checklist ticked, and the report-back note.
